02

Antes de ComeçarConta, custos e acesso

Três coisas antes de tocar em qualquer serviço — evitam tanto uma conta comprometida quanto uma surpresa na fatura.

Ative o MFA na conta root

A conta root da AWS pode fazer qualquer coisa, sem limite. Ative a autenticação em dois fatores nela (IAM → Security credentials → MFA) e nunca mais faça login nela no dia a dia.

Crie um usuário IAM para o trabalho diário

Em IAM → Users, crie um usuário (ex.: joao-admin) com a policy gerenciada AdministratorAccess — só para você, nunca para uma aplicação. É esse usuário (não o root) que você usa para logar no console e configurar o AWS CLI.

Configure um alarme de orçamento

Em Billing → Budgets, crie um budget de valor baixo (ex.: US$ 5) com alerta por e-mail em 80% e 100%. Leva 2 minutos e é a rede de segurança contra qualquer recurso esquecido ligado.

Instale e autentique o AWS CLI

terminal
# instala (Linux)
curl "https://awscli.amazonaws.com/awscli-exe-linux-x86_64.zip" -o "awscliv2.zip"
unzip awscliv2.zip && sudo ./aws/install

# autentica com o usuário IAM criado acima
aws configure
# Access Key ID, Secret Access Key, região (ex.: sa-east-1), formato: json
Nunca coloque Access Key/Secret Key em código versionado. Se algo for commitado por engano, revogue a chave na hora em IAM → Users → Security credentials.

04

Parte 1 — Publicar o FrontendO que já existe no repositório

Duas formas válidas de hospedar um SPA estático na AWS. A recomendação é AWS Amplify Hosting: menos peças para gerenciar, CI/CD automático a cada git push, e HTTPS de graça.

Recomendado Amplify Hosting

  • Conecta direto no GitHub — build e deploy automáticos
  • CDN (CloudFront) e SSL inclusos, sem configurar nada
  • Preview de cada branch/PR

Alternativa S3 + CloudFront manual

  • Mais peças: bucket, OAC, distribuição, invalidação de cache
  • Mais controle fino — útil só se o Amplify não servir seu caso
  • Requer pipeline próprio (GitHub Actions) para o deploy

4.1 · Passo a passo — Amplify Hosting

Confirme que o repositório está no GitHub

O Amplify builda direto da branch main. Se o projeto ainda for só local, crie o repositório remoto e dê push antes de continuar.

Console AWS → Amplify → New app → Host web app

Autorize o GitHub, selecione o repositório Site-MB-Treinamento-Neves e a branch main.

Configure o build — o app vive em frontend/

Como o projeto é um monorepo (site na raiz, código em frontend/), aponte o app root para frontend ou cole este amplify.yml na raiz do repositório:

amplify.yml
version: 1
applications:
  - appRoot: frontend
    frontend:
      phases:
        preBuild:
          commands:
            - npm ci
        build:
          commands:
            - npm run build
      artifacts:
        baseDirectory: dist
        files:
          - '**/*'
      cache:
        paths:
          - node_modules/**/*

Deploy

Clique em Save and deploy. Em poucos minutos o site fica no ar em um endereço https://main.xxxxxxx.amplifyapp.com, já com HTTPS.

Domínio próprio (opcional)

Em App settings → Domain management, adicione seu domínio. Se ele já está no Route 53, o Amplify cria os registros DNS e o certificado ACM sozinho — só confirmar.

A partir daqui, todo git push na main gera um novo deploy automático. Sem servidor para você gerenciar.

4.2 · Alternativa — S3 + CloudFront (manual)

Use este caminho só se precisar de controle que o Amplify não oferece. Resumo dos passos:

Bucket S3 privado

Crie um bucket (ex.: mb-consultoria-site) com Block Public Access ligado — o bucket nunca fica público diretamente.

Distribuição CloudFront com OAC

Crie uma distribuição apontando para o bucket, usando Origin Access Control (OAC) — só o CloudFront lê o bucket, o público nunca acessa o S3 direto.

Certificado ACM + domínio

Peça o certificado em us-east-1 (obrigatório para CloudFront), associe à distribuição e aponte o Route 53 para ela.

Deploy via GitHub Actions

.github/workflows/deploy-frontend.yml
name: Deploy Frontend
on:
  push:
    branches: [main]
    paths: ['frontend/**']
jobs:
  deploy:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: cd frontend && npm ci && npm run build
      - uses: aws-actions/configure-aws-credentials@v4
        with:
          aws-region: sa-east-1
          role-to-assume: ${{ secrets.AWS_DEPLOY_ROLE }}
      - run: aws s3 sync frontend/dist s3://mb-consultoria-site --delete
      - run: aws cloudfront create-invalidation --distribution-id ${{ secrets.CF_DIST_ID }} --paths "/*"

Parte 2 — Backend (Fase 2)Quando a API Spring Boot existir

Esta seção é preparação, não uma tarefa de hoje. Volte aqui quando o backend do documento de engenharia (Spring Boot + PostgreSQL) estiver escrito.

Para uma API Spring Boot de porte pequeno/médio, Elastic Beanstalk é o caminho mais simples: você envia um .jar, a AWS cuida de EC2, monitoramento e (opcionalmente) balanceamento de carga.

Crie o banco primeiro — RDS PostgreSQL

Console → RDS → Create database → PostgreSQL → template Free tier → classe db.t3.micro (ou t4g.micro). Em Connectivity, marque Public access: No — o banco só deve ser alcançável de dentro da VPC, nunca da internet.

Ambiente Elastic Beanstalk — plataforma Java

Console → Elastic Beanstalk → Create application → plataforma Java (Corretto). Para o menor custo em desenvolvimento, escolha Environment type: Single instance (sem load balancer). Migre para Load balanced só quando precisar de alta disponibilidade real.

Libere só a porta 5432 para o Beanstalk

No Security Group do RDS, adicione uma regra de entrada na porta 5432 que aceite tráfego apenas do security group das instâncias EC2 do Beanstalk — nunca 0.0.0.0/0.

Credenciais como variáveis de ambiente

Em Configuration → Software, defina as propriedades de ambiente — nunca no application.properties commitado:

variáveis de ambiente
SPRING_DATASOURCE_URL=jdbc:postgresql://SEU-ENDPOINT-RDS:5432/mb_consultoria
SPRING_DATASOURCE_USERNAME=mb_admin
SPRING_DATASOURCE_PASSWORD=valor gerado, não versionado
JWT_SECRET=chave longa e aleatória, só nesta variável

Para produção, migre JWT_SECRET e a senha do banco para o AWS Secrets Manager, e leia via SDK — as variáveis de ambiente do EB já resolvem para o início.

Deploy do .jar

terminal
cd backend
./mvnw clean package -DskipTests
eb init -p corretto-21 mb-consultoria-api
eb create mb-api-env --single --envvars SPRING_PROFILES_ACTIVE=prod
eb deploy

CORS restrito ao domínio do frontend

No Spring Security, libere apenas a origem real do site (Amplify ou seu domínio) — nunca *. Isso é exatamente a camada "CORS" já prevista no plano de segurança do documento de engenharia.

5.1 · Fotos das turmas — S3 ou Cloudinary

O documento de engenharia já previu um serviço externo de imagens (ex.: Cloudinary) para o banco não guardar arquivos pesados. Duas opções válidas, sem contradizer aquele plano:

OpçãoQuando usar
Manter CloudinaryMais simples para upload direto do navegador (widget pronto, transformação de imagem inclusa).
Trocar por S3 + CloudFrontJá que o resto está na AWS — um bucket + URLs assinadas via backend, sem outro fornecedor para gerenciar.

Glossário AWS

Amplify Hosting
Serviço que builda e publica um frontend a partir do Git, com CDN e SSL inclusos.
S3
Armazenamento de arquivos (bucket) — guarda tanto o site estático quanto imagens.
CloudFront
CDN da AWS — entrega o conteúdo a partir do ponto mais perto do visitante.
Route 53
Serviço de DNS e registro de domínio da AWS.
ACM
Certificate Manager — emite e renova certificados HTTPS de graça.
Elastic Beanstalk
Orquestra EC2 + deploy para uma aplicação (aqui, o .jar do Spring Boot).
RDS
Banco de dados gerenciado — aqui, PostgreSQL sem precisar administrar o servidor.
Security Group
Firewall por recurso — define quem pode falar com quem, em qual porta.
IAM
Controle de identidade e permissões — quem pode fazer o quê na conta.
Secrets Manager
Guarda senhas e chaves fora do código, com acesso controlado por IAM.
